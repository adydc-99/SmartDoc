# 资料库排序参数与上传后刷新修复设计

## 问题

资料库前端使用 `updated-desc`、`name-asc` 等连字符排序值，并将该值直接传给 `/api/library/documents`。后端排序解析器只接受逗号、冒号或下划线分隔，因此默认资料列表请求返回 `400 Unsupported library sort`。上传请求结束后，上传队列依赖资料列表刷新判断解析状态；列表请求失败会使上传看起来一直未完成。

## 目标

- 资料库、收藏和最近阅读入口使用默认及显式排序时均能正常加载。
- 上传后刷新能够取得最新资料并更新上传队列状态。
- 已存在的连字符 URL/API 调用继续可用。
- 用户能够看到后端返回的安全、具体错误消息。

## 设计

### 前端协议转换

界面和 URL 继续使用现有的 `updated-desc`、`updated-asc`、`name-asc`、`name-desc`，避免破坏路由状态和组件选项。调用资料列表 API 时，将排序值显式转换为后端规范值：

- `updated-desc` → `updated,desc`
- `updated-asc` → `updated,asc`
- `name-asc` → `name,asc`
- `name-desc` → `name,desc`

转换只发生在 API 边界，不改变 Pinia store 和地址栏格式。

### 后端兼容解析

后端排序解析器接受逗号、冒号、下划线和连字符四种分隔符。字段与方向白名单保持不变，未知值仍返回 400，避免把兼容处理扩大为任意排序表达式。

### 错误反馈

资料列表和上传队列从 Axios 响应的安全 `message` 字段提取错误；没有结构化消息时才回退到通用网络错误。不得展示堆栈、内部路径或密钥。

## 测试

- 后端测试先证明 `updated-desc` 当前失败，再验证四种分隔格式和非法排序拒绝行为。
- 前端测试先证明 API 边界仍发送连字符值，再验证它发送规范逗号值且不修改原筛选对象。
- 上传队列测试验证后端安全错误消息能够显示。
- 最后运行后端、前端全量测试和前端生产构建。

## 非目标

- 不修改上传大小、文件类型或解析逻辑。
- 不修改数据库或执行 SQL。
- 不重构整个资料库状态管理。
